# Task Manager — Next.js 15 + tRPC

A simple task management app built for a technical challenge. The back-end keeps
tasks **in memory** and exposes them through **tRPC**; the front-end uses
**Next.js 15 (App Router)**, **React 19**, **TanStack Query** and **Material UI**.

The repository is a small monorepo (npm workspaces) with two folders:

- **`back-end/`** (`@task-manager/back-end`): everything server-side — the tRPC router,
  business rules, validation (Zod) and the in-memory store.
- **`front-end/`** (`@task-manager/front-end`): the Next.js app — pages, components and
  the tRPC client.

It is still **a single Next.js application**: the front-end's `/api/trpc` route only mounts
the HTTP handler provided by the back-end, so `npm run dev` starts everything in one process.

## Getting started

Requirements: Node.js 22.12+ (needed by the test runner; the app itself runs on 18.18+).
Run the commands from the **repository root**.

```bash
npm install
npm run dev
```

Open <http://localhost:3000>.

Production build:

```bash
npm run build
npm start
```

Type-check both packages:

```bash
npm run typecheck
```

Run the tests:

```bash
npm test
```

> The app starts with 25 sample tasks so the list and the infinite scroll can be seen
> right away. Since data lives in memory, **everything is lost when the server restarts**.

> In development every tRPC call has an artificial 400 ms delay so the loading states are
> visible. Disable it with `TRPC_DELAY_MS=0 npm run dev`.

## Data model

```ts
type Task = {
  id: string;           // UUID generated by the server
  title: string;        // required, 1–100 characters (after trimming)
  description?: string; // optional, up to 500 characters
  status: "not_started" | "in_progress" | "done"; // default: "not_started"
  createdAt: Date;      // set by the server; immutable
};
```

The screens folder is called `views/` and not `pages/` on purpose: in Next.js, a `src/pages`
folder enables the Pages Router and would turn every file into a public route.

The back-end package exposes three entry points (`exports` in `back-end/package.json`):

| Entry point | Used by | Contents |
|---|---|---|
| `@task-manager/back-end` | Server Components | router, `createCaller`, types |
| `@task-manager/back-end/http` | `/api/trpc` route | HTTP handler |
| `@task-manager/back-end/schemas` | server **and** browser | Zod schemas, types and constants |

## How SSR works on the list page

1. `app/page.tsx` is a Server Component. It calls `prefetchInfiniteQuery` for the first page
   of tasks, calling the tRPC router **directly** (no HTTP round-trip to itself).
2. The result is stored in a per-request React Query cache (`cache(makeQueryClient)`), so
   data never leaks between users.
3. `HydrateClient` serializes that cache (with superjson, so dates stay `Date` objects) into
   the HTML.
4. In the browser, `TaskListView` calls `useInfiniteQuery` with **the same options**, so it
   finds the hydrated data under the same query key and renders without a new request.
   From then on everything runs on the client (infinite scroll, status changes, deletion).

The page uses `force-dynamic` because the data changes on every operation and must not be
cached at build time.

## Key design decisions

- **tRPC v11 + `@trpc/tanstack-react-query`**: the current official integration. It exposes
  typed `queryOptions`/`mutationOptions` that plug straight into TanStack Query hooks, giving
  end-to-end type safety without code generation.
- **Shared Zod schemas**: the same schema validates the tRPC input and the form, so rules and
  messages never drift apart. Even if front-end validation is bypassed, the server rejects the
  request with `BAD_REQUEST`, and per-field errors (`data.zodError.fieldErrors`) are shown
  next to the matching field.
- **Cursor-based pagination**: each task gets an internal, never-reused sequence number used
  as the cursor. Unlike an offset, it doesn't skip or duplicate items when tasks are deleted
  between loading two pages.
- **Optimistic status updates**: changing a status updates the UI immediately; if the server
  rejects it, the previous value is restored and an error toast is shown. A dedicated
  `changeStatus` procedure avoids re-sending the title and description.
- **Infinite scroll with `IntersectionObserver`**: a sentinel element at the end of the list
  triggers the next page (no scroll listeners), with a "Load more" button as an accessible fallback.
- **Back-end / front-end split in one Next.js app**: code is separated by responsibility (the
  back-end has no React or Next.js dependency) without the cost of running two servers. The
  back-end is plain TypeScript with no build step; Next.js compiles it via `transpilePackages`.
  Splitting into two services later only requires serving `back-end/src/http.ts` on its own
  server and pointing the tRPC client to it.
- **Material UI (v9)**: mature, accessible components (Dialog, Tooltip, Snackbar, Menu, Card…)
  and a single theme. `AppRouterCacheProvider` collects Emotion styles during SSR, so pages
  render styled with no flash; light/dark mode follows the OS through CSS variables.
- **Store on `globalThis`**: keeps data across Next.js hot reloads in development.
- **superjson**: preserves `Date` values (`createdAt`) between server and client.
- **Fixed locale and time zone for dates**: guarantees the server and the browser render the
  same HTML, avoiding hydration mismatches.
- **No form library**: form state uses `useState` (as the challenge asks for functional
  components and hooks); with three fields a library would not pay off.

## Accessibility

- Icon-only actions (edit/delete) have an `aria-label` with the full name (e.g. "Edit task: X")
  and a tooltip shown on hover **and** keyboard focus, dismissible with Esc.
- The status chip is a menu button (`aria-haspopup`, `aria-expanded`) operable with the
  keyboard (arrows, Enter, Esc) that returns focus to the chip.
- Dialogs trap focus, close with Esc and return focus to the element that opened them.
- Form fields are wired to their label, helper text and error state automatically.
- Status is never conveyed by color alone (colored dot + label), the palette was checked for
  color-vision deficiencies, and `prefers-reduced-motion` is respected.

## Tests

Unit tests use [Vitest](https://vitest.dev/) (`npm test` runs both packages; `npm run test:watch -w <package>`
re-runs on save). 39 tests:

| File | What it covers |
|---|---|
| `back-end/src/schemas.test.ts` | Validation rules: required/trimmed title, length limits, empty description → `undefined`, default status, valid statuses and ids |
| `back-end/src/store.test.ts` | Create (server-generated id/date), newest-first listing, **cursor pagination without skipping or repeating tasks even after a deletion between pages**, update/changeStatus/delete and missing-task cases |
| `back-end/src/routers/task.test.ts` | The tRPC router through `createCaller` (the same path used by SSR): full CRUD flow, `BAD_REQUEST` for invalid input, `NOT_FOUND` for missing tasks; and the real HTTP handler's error format (readable message + per-field errors, 404 status) |
| `front-end/src/lib/format.test.ts` | Description truncation (word boundary, hard cut, limit) and the fixed-time-zone date format |

To make the store testable in isolation, `store.ts` exports a `createTaskStore()` factory; the
app uses one seeded instance, while each test starts from a fresh, empty store.

## Trying the error handling manually

- Submit the form with an empty title (or only spaces) → inline error, no request is sent.
- Open `/tasks/<non-existent-id>/edit` → 404 page.
- Open a task's edit page in one tab, delete it in another and save in the first →
  the server responds `NOT_FOUND`, shown in the form and in a toast.
- Delete the same task in two tabs → the second shows an error toast and the list resyncs.

## Limitations and next steps

- **Persistence**: data lives in memory and is lost on restart; it also wouldn't work with
  multiple server instances. Next step: a database (e.g. PostgreSQL with Prisma or Drizzle)
  behind the same `taskStore` interface — no other file would need to change.
- **Authentication**: there are no users; anyone can edit any task.
- **More tests**: the business logic and the API are unit-tested; next steps would be
  component tests (Testing Library) for the form and the list, and an end-to-end flow
  (Playwright) covering create → edit → change status → delete, plus running everything in CI.
- **Time zone**: dates are shown in a single fixed time zone; a global product would store
  each user's time zone.
